# avyoats.com one-page Jumpstart Pro app research report

## Recommendation

avyoats.com is a good fit for a **public, read-only, single-page Rails app** whose job is to answer one question quickly: “What do I need to know before I drive up for a tour?” The strongest implementation choice is a **mobile-first long-scroll dashboard** with four source layers: the Utah Avalanche Center Salt Lake forecast JSON for the avalanche rose, a station-observation adapter for Snowbird weather data, a forecast fallback for cloud cover and UV when the station does not expose them, and a curated set of canyon and resort webcam tiles. That approach is feasible because the avalanche forecast is officially documented, the Snowbird station exists in public weather catalogs, UDOT publishes canyon camera locations, and the resort sites already expose webcam pages. citeturn1view0turn0search2turn36search1turn23view3turn23view0turn23view2turn34view0

The most important product decision is **not** visual. It is whether the app promises “everything from one station” or clearly separates **measured station observations** from **forecast-derived values**. That matters because the official station/weather tooling says data availability varies by station, and because official UV products are generally published as a **daily/noon-oriented forecast**, not a native half-hour station observation. In practice, that means temperature, wind speed, and wind direction are natural fit metrics for the Snowbird station graph, while cloud cover and especially UV should be labeled more carefully if they come from forecast data rather than the station itself. citeturn20view0turn29search2turn29search7turn30search2turn30search8

## Data sources that fit the product

For the avalanche block, the source of truth should be the **Utah Avalanche Center Salt Lake forecast JSON**. UAC documents the endpoint pattern as `/forecast/[region]/json`, and `salt-lake` is one of the supported region slugs. UAC also documents how the rose is encoded: the array begins at the highest-elevation north aspect, proceeds clockwise, and the `overall_danger_rose` values map to a 0–10 danger scale. UAC explicitly asks integrators to send a proper User-Agent and to poll sanely, noting that forecasts are generally issued between 5 and 8 a.m. and are rarely updated after publication. That is exactly the shape of data a public “quick reference” page needs. citeturn1view0turn32search0

For weather, the cleanest observation layer is entity["company","Synoptic Data","weather data platform"], because its documented Weather API provides `latest`, `timeseries`, and `metadata` services under `/v2/`, and the time-series service supports `start`/`end` or `recent`, local-time output, English units, and QC-aware responses. Synoptic’s public docs also make clear that a **token is required**, which means avyoats.com should proxy weather requests server-side instead of exposing a token in browser JavaScript. The Snowbird station is publicly discoverable as **SBDU1 / SNOWBIRD**, sourced from the NRCS SNOTEL network, which is enough to justify building a dedicated station adapter around it. citeturn11search1turn13view0turn12search1turn11search4turn36search1

As a second weather layer, the entity["organization","National Weather Service","us weather agency"] is valuable for forecast and fallback data. Its API is open data, free to use, cache-friendly, and requires a User-Agent. The `/points/{lat},{lon}` lookup returns `forecastHourly` and `forecastGridData` endpoints, which makes it suitable for forecast-derived values if the station does not expose every variable you want. Separately, the NWS Western Region time-series viewer documents that station pages can chart temperature, wind direction, wind speed and gusts, solar radiation, and cloud information, but it also says data availability varies by station. That is a strong signal to architect measured and forecast data as separate feeds rather than forcing every graph through one source. citeturn31view0turn20view0

For cloud cover specifically, an additional forecast fallback such as Open-Meteo is practical because its official docs expose **hourly** temperature, total cloud cover, wind speed, and wind direction variables. The same docs show **UV index as a daily variable**, not a half-hour observational station metric. That lines up with EPA/FDA guidance that the UV Index is a daily forecast product intended to describe expected UV intensity during the day, especially around solar noon. My conclusion is that a “half-hour UV graph at the Snowbird weather station” is the weakest part of the current requirements and should either be removed, relabeled as forecast-derived, or replaced with a simpler daily max UV card. citeturn29search0turn29search2turn29search7turn30search2turn30search8

For webcams, the source mix is unusually good. The UAC Salt Lake mountain weather page already surfaces **Alta Snow Stake**, **Snowbird Snow Stake**, and **Brighton Top of Crest** camera tiles. The official Brighton conditions page lists live cams including **Molly Green’s**, **Top of Crest 6**, **Milly Express**, and **Bottom of Majestic Lift**. Alta’s weather page explicitly includes **Mountain Cams**. Snowbird’s webcam page currently exposes at least **Snowstake Webcam** and **Little Cloud Webcam**. And entity["organization","Utah Department of Transportation","utah state agency"] publishes a canyon road-information page with named camera locations throughout both canyons. citeturn26view0turn23view0turn23view2turn34view0turn23view3

The canyon camera coverage is strong enough that avyoats.com does not need every camera. UDOT’s page lists Little Cottonwood locations such as the SR-209/SR-210 intersection, Upper Vault, Seven Turns, White Pine, Alta Bypass, and Alta, and Big Cottonwood locations such as Wasatch, Dogwood, S-Curves, Cardiff Fork, Silver Fork, Solitude, and Brighton Circle. For a fast-reference tool, a smaller set of representative tiles is better: one or two road-entry cameras, one mid-canyon camera, one upper-canyon camera, plus the resort/snow-stake views that show surface conditions. citeturn23view3

## Product shape for a one-page tour dashboard

The page should feel like a **field card**, not a portal. I would structure the scroll in this order: a small masthead with the avyoats.com brand and last refresh time; a fixed-height “go / caution / stop and think” avalanche strip with the Salt Lake avalanche rose and short forecast timestamp; a weather section with four compact charts; a camera strip for Little Cottonwood; a camera strip for Big Cottonwood; a resort-cam strip for Brighton, Alta, and Snowbird; and finally an optional footer with source attribution and click-outs. The point is to make the page scannable in a parking lot or at a stoplight, not to reproduce every source site.

The weather block should use **measured vs forecast badges**. The most honest version is: **measured** temperature, wind speed, and wind direction from the Snowbird station; **forecast-derived** cloud cover; and either **daily UV max** or no UV graph at all. If UV remains in scope, it should be visually separated so users do not assume it is a station observation. That small labeling decision will make the product more trustworthy than pages that merge everything into one unlabeled weather graph. citeturn20view0turn29search2turn29search7turn30search2

The brown-and-tan aesthetic is appropriate, but it should be paired with strict readability rules. Use sand, clay, walnut, and off-black tones, but keep body text and important labels at or above WCAG contrast thresholds. entity["organization","W3C","web standards body"]’s guidance explains the accessibility rationale for the 4.5:1 contrast floor for normal text, which matters here because this app will be used outdoors, in bright light, on phones. A muted palette is fine; low-contrast typography is not. citeturn25search1turn25search3

## Rails and Jumpstart Pro architecture

The attached project summary is useful as **build context**, but it should not define the tenancy model for avyoats.com. That document describes a **Jumpstart Pro Rails 8** application, explicitly says it is **multi-tenant**, and says account data is scoped through `acts_as_tenant`. It also documents a frontend stack of **Hotwire (Turbo + Stimulus)**, **Tailwind**, **Import Maps**, and **Chart.js**. For avyoats.com, the right move is to **reuse the Rails/Hotwire/Tailwind/import-map/charting stack** and deliberately **drop the account-scoped tenancy patterns**. This should be a single public app, not an account platform with user switching, admin tenancy, or multi-account selectors. fileciteturn0file0L17-L21 fileciteturn0file0L600-L603

In concrete terms, I would build one public `HomeController#show` page and three thin source adapters behind it: an avalanche adapter for UAC, a weather adapter for the Snowbird station plus forecast fallback, and a cameras adapter that normalizes the handful of chosen camera cards. Keep the HTML server-rendered, use Turbo only for partial refreshes, and load charts through a Stimulus controller. That keeps the app aligned with the attached Jumpstart-style stack while staying much simpler than the uploaded multi-tenant repo. fileciteturn0file0L600-L603 citeturn1view0turn13view0turn31view0turn23view3

The cache strategy should be source-aware. UAC has its own explicit polling guidance, so the avalanche forecast should be cached aggressively and refreshed on the forecast cycle rather than on every page request. Weather observations can refresh more often, but still through server-side caching rather than client fan-out. Forecast fallbacks should honor the NWS API’s cache-friendly design. In practice that means avyoats.com should look like a live page, but architecturally behave like a small aggregation service with predictable refresh intervals and a single user-agent identity to each provider. citeturn1view0turn31view0turn13view0

## Operational constraints and source risks

The main technical risk is **camera embedding stability**. The public pages are there, but they are not all documented as stable embed APIs. In testing-like fetches, direct UDOT camera links returned **403 Forbidden**, and a Snowbird snapshot URL returned **404** even though the parent webcam page exists. That strongly suggests you should not assume every provider supports direct hotlinking. The safe design is a **per-source adapter**: use direct image URLs where they work, fall back to page links or provider pages where they do not, and always render camera tiles so the page still works even if one provider changes its embed path. citeturn33view0turn33view1turn27view1turn34view0turn23view0turn23view2

The second risk is **weather variable mismatch**. The Snowbird station clearly exists, and the weather tooling clearly supports time-series data, but the official station-view tooling also says variable availability differs by station. That means the product should avoid promising “Snowbird station graphs for windspeed, direction, cloud cover, UV, and temperature” until you confirm the exact measured variables you want from that station feed. The safer requirement is “Snowbird-centered weather graphs,” with measured and forecast badges. citeturn36search1turn13view0turn20view0

The third risk is **UV wording**. Official UV guidance describes the UV Index as a forecast scale tied to expected daytime intensity, especially around noon, and Open-Meteo’s docs expose UV as a daily forecast variable. So if the product keeps a half-hour UV graph, it will almost certainly be an estimated or interpolated forecast presentation rather than a station observation. That is not inherently wrong, but it should be represented honestly in the UI. citeturn29search7turn30search2turn30search8

## Final build recommendation

The MVP I would approve is this: **a single public Rails page with no login, no multi-tenancy, and no account scoping; UAC Salt Lake avalanche rose at the top; three Snowbird-centered weather charts for temperature, wind speed, and wind direction; one forecast-derived cloud cover chart; a daily UV card instead of a half-hour UV chart; four to six UDOT canyon camera tiles; and one or two official resort tiles each from Brighton, Alta, and Snowbird.** That version is fast, honest about source types, and aligned with the existing Jumpstart-style Rails stack. citeturn1view0turn23view3turn23view0turn23view2turn34view0turn29search2turn29search7 fileciteturn0file0L600-L603

If you want a phase-two version, add canyon travel-time and sign data from the UDOT Cottonwoods page, historical weather windows, user-selectable favorite cameras stored in local storage, and a second alternate weather provider so the page can degrade gracefully if any one feed fails. UDOT’s current page already includes travel times and forecast links, so that enhancement would fit naturally without changing the one-page concept. citeturn23view3
